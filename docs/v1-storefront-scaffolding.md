# E10 storefront theme scaffold

Status: fixture-only frontend foundation, 17 October 2026. This slice does not complete V02, V05, E20 or SEO/publication acceptance. It changes only `frontend/storefront/` and this document. No backend routes, shared dependencies, auth, migrations, providers or production data were changed.

## Run locally

Requires Node 24 or another modern Node runtime. Runtime dependencies: none.

```sh
cd frontend/storefront
npm run dev
```

Open `http://127.0.0.1:4317/`. Use `?theme=editorial`, `?theme=catalogue` or `?theme=video`. The development server binds loopback only; override its port with `PORT=4318 npm run dev`. The directory can also be served by an ordinary static development server. Opening `index.html` directly as `file:` is unsupported because it uses ES modules.

The top toolbar changes theme without losing the in-memory bag. The boutique-name setting changes the header wordmark only; collection copy and footer remain the fictional Tara boutique. These changes are not saved across reloads. Publishing is unavailable with its missing prerequisites stated next to the disabled control.

## Delivered preview behavior

- Editorial occasionwear: generous cream/plum editorial composition with a large illustrated campaign panel.
- Everyday catalogue: sage collection banner, denser four-column desktop catalogue, search and category filters.
- Video-led boutique: deep-plum styling, vertical story presentation and a product-linked story dialog. This is an **illustrated story study**, with no video or seller footage connected. There is no pretend video playback.
- All themes share safe text rendering, product cards, size/colour selection, quantities, a bag, a checkout-preview summary and policy sections. They use the same six synthetic products and thirteen SKUs.
- Native dialogs support Escape, keyboard focus containment and focus restoration. The bag preserves focus while quantities change. Layout reflows to phones/tablets, provides labelled controls and respects reduced-motion settings.
- Every screen identifies preview data. Checkout collects no address or other personal data, does not submit a form, and cannot create orders, invoke Razorpay/COD, reserve stock or send messages.

All garment assets are original geometric SVG illustrations generated by `design/draw-assets.py`. They are not photos, imported seller media or verified descriptions of real products. The page loads no remote images, fonts, scripts or APIs. The local server sends a CSP that disables network connections and form submission.

## Contract boundary

`src/fixtures.js` exports `catalogueFixtures`, whose envelope and SKU field names align with the accepted `catalogue.v1` foundation contract:

```json
{
  "contract_version": "catalogue.v1",
  "mode": "preview_foundation",
  "business_id": "11111111-1111-4111-8111-111111111111",
  "product_id": "22222222-2222-4222-8222-222222222201",
  "name": "Gulab occasion set",
  "description": "Synthetic example",
  "category_id": "44444444-4444-4444-8444-000000000001",
  "photo_urls": ["./assets/rose.svg"],
  "readiness": {"state": "reviewed_sample", "issues": []},
  "checkout_enabled": false,
  "skus": [{
    "sku_id": "33333333-3333-4333-8333-333333333301",
    "product_id": "22222222-2222-4222-8222-222222222201",
    "options": {"Size": "S", "Colour": "Rose"},
    "price_minor": 689000,
    "currency": "INR",
    "stock_available": 2,
    "active": true
  }]
}
```

The **readiness object values/shape and options object shape are isolated fixture proposals**, pending exact backend schema agreement. They are not asserted as accepted server payloads. `src/catalogue-adapter.js` normalizes these fixture DTOs into presentation models. Unknown readiness fails closed, and a response with `checkout_enabled=true` is rejected by this preview adapter. No fetch or implicit switch to live data exists.

`business_id` uses the legacy `Seller.id` UUID compatibility bridge. Future writes must derive the authorized tenant from the route/auth context, never trust a request-body business ID. `commerce_orders` remains the canonical backend new-order writer; this frontend adds no writer.

`checkoutProposal()` is an **unsubmitted, unimplemented proposal**, with no endpoint associated with it:

```json
{
  "idempotency_key": "locally-generated-uuid",
  "items": [{"sku_id": "33333333-3333-4333-8333-333333333301", "quantity": 2}]
}
```

It includes no business ID, customer, price, discount, total, payment method or credentials. Its local key is discarded after preview validation; real integration must agree the exact write schema and persist/reuse an idempotency key for retries. Backend checkout must reread authoritative SKU prices, currency, stock and policies, calculate totals, lock/reserve correctly, and return canonical order/payment state. Client subtotal is explicitly a sample estimate; shipping/tax/destination/payment support remains unimplemented.

## Inventory and privacy rules

- `stock_available` is available units, never on-hand quantity. Positive integer stock caps the aggregate quantity of a single SKU across the bag. Zero is sold out.
- Null stock on a reviewed, active SKU means **untracked**, not zero and not unresolved inventory. The preview applies a stated implementation guard of 10 items per untracked SKU; it is not a claim of available stock or a platform inventory policy.
- Legacy variants needing stock allocation use the separate proposed readiness state `variant_stock_review`; all their SKUs are inactive. Null is never used by itself to infer review. Unknown readiness, invalid numeric data and inactive SKUs cannot be added.
- Aggregate legacy stock is never copied or multiplied across variants. Sample SKU quantities are synthetic and independently set.
- The preview supports INR only. Unsupported or mixed-currency SKUs fail closed instead of silently contributing to an INR subtotal.
- Public fixtures have a strict public field shape. Floor prices, private notes, credentials and gateway data are absent. User-controlled product/name/policy strings are inserted as text nodes, never HTML. The fixture-only asset mapping is local and does not implement a production remote-media policy.

## Validation and evidence

Run:

```sh
npm ci --ignore-scripts
npm run check
npm test
npx playwright install chromium
npm run test:browser
```

A preinstalled browser can be used with `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/absolute/path/to/chromium npm run test:browser`. `@playwright/test` is the only development dependency, scoped to this standalone directory. Browser downloading is not part of app runtime.

Observed on Node 24.20.0, npm 11.19.0, Playwright 1.58.2 using cached Chromium 1243:

- Syntax checks passed.
- Seven contract tests passed: public DTO shape/privacy, stock distinctions, aggregation/caps, bad quantities/unknown SKUs, inactive/currency rejection, readiness fail-closed, and proposal allowlist.
- Eight browser tests passed with one worker: each of three themes at 1440px and 390px completes browse → size/stock selection → quantity-capped bag → honest checkout preview → removal/empty bag and keyboard Escape/focus checks, including product detail returning focus to its triggering product button; additional tests cover untracked/review states, theme bag parity, wordmark injection safety, illustrated story honesty, and overflow at 320px/768px with settings open.
- Browser journeys observed no external requests, non-GET requests or JavaScript errors.
- An initial browser pass found a nested-dialog focus restoration issue. The fix returns Escape focus to the header bag control; the final complete pass verifies it.

`design/study.html` and `design/study.png` are the preimplementation visual study, inspected before production scaffold code was written. The six `design/{editorial,catalogue,video}-{desktop,mobile}.png` images show the actual tested scaffold. Screenshots are regenerated by browser tests and are review evidence, not a deployed site.
