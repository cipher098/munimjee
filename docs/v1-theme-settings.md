## Semantics and API

All routes require `V1_AUTH_ENABLED`. Reads require a current native `v1_user` session and `catalogue.read`; changes use shared `business_mutation("business.write")`, whose yield guard validates the native session/origin/CSRF and current role before execution and again before the caller commits, including exact receipt replay (owner/manager). Viewer and staff are read-only. Tenant/actor/reviewer IDs in bodies are forbidden. The route business ID is checked against the current active user, membership, business and seller.

- `GET /v1/businesses/{business_id}/themes`: native editor.
- `GET /api/v1/businesses/{business_id}/theme-settings`: `{version,draft,published,published_revision,published_at}`; absent row is version 0, catalogue/forest defaults, no published design.
- `PUT .../theme-settings`: `{expected_version,idempotency_key,config}` saves a private draft.
- `POST .../theme-settings/publish`: `{expected_version,idempotency_key}` copies the saved draft to the published configuration and advances the version/publication revision.
- `GET .../theme-settings/preview`: authenticated saved-draft HTML, noindex/no-store, restrictive CSP, escaped text, no checkout scripts/API and no draft product data. Query parameters never supply theme or commerce authority.

**Design publication is separate from `Storefront.published`.** It never creates a Storefront, activates products, changes inventory, enables checkout or changes payment methods. A saved draft never changes the published helper's output. A design may be published while the store remains private; only the existing store-publication authority determines whether any public route is visible. Product/category URLs and COD behavior stay under existing authorities. Public helper fallback for a tenant without a published design is catalogue with blank configured text (existing theme defaults).

Config has exactly `theme` (`editorial/catalogue/video`), `palette` (`rose/forest/indigo`), plain-text `brand_tagline`, `hero_eyebrow`, `hero_headline`, `hero_intro`, `collection_heading`, `story_heading`, `story_body` and strict boolean `show_story/show_categories`. HTML/CSS/JS and arbitrary image/video/link URL fields are absent and rejected as extras. Text lengths and control/markup characters are checked server-side. Shipping/return policies remain in the existing store settings. No seller video upload or real media claim is introduced.

## Persistence and replay

`StorefrontThemeSettings` (`storefront_theme_settings_v1`) has a tenant primary key, version, draft/published JSONB, publication revision/time and last editor. `StorefrontThemeCommand` (`storefront_theme_commands_v1`) has `(business_id,idempotency_key)` primary key, operation, canonical request hash, immutable result, actor and creation time. No receipts are evicted. A different actor/body/operation reusing a key returns 409. The original actor with current write access can replay the exact command after newer changes and receive the original receipt; the editor subsequently fetches current state so it never hydrates that old result as the current version.

Writes lock the existing Business row to serialize first insert as well as later writes, then recheck access. The shared yield dependency also rejects native session revocation during that wait, and rolls back staged changes or refuses a receipt replay when session/role is revoked after the service returns but before commit. Version mismatch returns 409 and performs no state change. Both settings and receipt commit in the caller's transaction; no service commits independently. Versions monotonically increase for save and publish, with a bounded upper limit. Receipt records provide actor/operation attribution without inventing a shared audit schema.

The browser persists only an outstanding command in sessionStorage under `munimjee.v1.theme-command:<user>:<business>`. It stores a hash of the session CSRF value, not the token itself, and a payload digest. Startup validates identity, tenant, schema, digest and a seven-day recovery window before enabling retry. It never replays automatically. Storage failure sends no new command. A terminal identity fence clears every owned theme prefix, the form, preview and displayed private state; generation checks and post-response session checks prevent delayed responses from restoring private data. Preparation/retry locks prevent rapid actions from issuing competing keys. A stale-write response requires explicit reload. This page offers saved-draft preview, with unsaved changes clearly labelled until saved.

## Application composition

The reserved actual revision is `0049_v1_storefront_settings`, with exact committed predecessor `0048_v1_parcel_tracking`. It creates both JSONB tables with the model primary/FK/check constraints; no predecessor is invented and no `create_all` evidence is used. The coordinator registers `app.models.storefront_theme_v1`, mounts the router, packages `theme_settings.html/css/js`, adds the native navigation links, and extends shared authentication cleanup with `munimjee.v1.theme-command:`. Those shared files are outside this lane. The owned page independently fences identity, tenant, native auth method, session digest and late responses. HTTP403 during recovery retains the immutable uncertain command for later authorization; it never starts a new key automatically.

Delegated public hooks are implemented in the canonical provider, actual SSR renderer and actual live renderer. After existing store/tenant publication checks, `PublishedStorefrontProvider` calls only `published_theme`, which validates the saved published configuration. Drafts, editor/tenant IDs, command receipts and version history never enter `PublicStorefront.design`. Its `theme` now comes from this persisted publication; no constructor/query override wins over the seller's saved design.

SSR revalidates the exact allowlist through `v1/storefront/design.py`; the DOM renderer separately validates the same public shape through `src/published-design.js`. The latter is an explicit runtime dependency for coordinator packaging. Both use fixed `palette-rose/forest/indigo` classes and predefined tokens. Blank hero/collection text uses existing theme defaults; default story uses public store description. Text is escaped in SSR and emitted as DOM text nodes. Private saved-draft previews use the same hero/collection defaults and fixed palette classes, retain illustrative placeholders and no checkout scripts/forms/API.

The three existing layout treatments remain: editorial serif hero/three-column collection, compact catalogue hero/four-column collection, and studio arch hero. The video collection's prior hardcoded dark background is replaced by the selected palette's paper token so every palette remains readable. No seller video/media upload or real footage is introduced. `show_story/show_categories` change presentation only: public product/category records, canonical routes, COD/online handoff and private order-status authority remain intact. Existing checkout-attempt, payment-handoff, checkout-session and order-status implementations were not edited.
