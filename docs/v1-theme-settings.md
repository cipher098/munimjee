## Semantics and API

All routes require `V1_AUTH_ENABLED`. Reads require a current native `v1_user` session and `catalogue.read`; changes require shared `require_v1_mutation` session/origin/CSRF validation plus freshly checked `business.write` (owner/manager). Viewer and staff are read-only. Tenant/actor/reviewer IDs in bodies are forbidden. The route business ID is checked against the current active user, membership, business and seller.

- `GET /v1/businesses/{business_id}/themes`: native editor.
- `GET /api/v1/businesses/{business_id}/theme-settings`: `{version,draft,published,published_revision,published_at}`; absent row is version 0, catalogue/forest defaults, no published design.
- `PUT .../theme-settings`: `{expected_version,idempotency_key,config}` saves a private draft.
- `POST .../theme-settings/publish`: `{expected_version,idempotency_key}` copies the saved draft to the published configuration and advances the version/publication revision.
- `GET .../theme-settings/preview`: authenticated saved-draft HTML, noindex/no-store, restrictive CSP, escaped text, no checkout scripts/API and no draft product data. Query parameters never supply theme or commerce authority.

**Design publication is separate from `Storefront.published`.** It never creates a Storefront, activates products, changes inventory, enables checkout or changes payment methods. A saved draft never changes the published helper's output. A design may be published while the store remains private; only the existing store-publication authority determines whether any public route is visible. Product/category URLs and COD behavior stay under existing authorities. Public helper fallback for a tenant without a published design is catalogue with blank configured text (existing theme defaults).

Config has exactly `theme` (`editorial/catalogue/video`), `palette` (`rose/forest/indigo`), plain-text `brand_tagline`, `hero_eyebrow`, `hero_headline`, `hero_intro`, `collection_heading`, `story_heading`, `story_body` and strict boolean `show_story/show_categories`. HTML/CSS/JS and arbitrary image/video/link URL fields are absent and rejected as extras. Text lengths and control/markup characters are checked server-side. Shipping/return policies remain in the existing store settings. No seller video upload or real media claim is introduced.

## Persistence and replay

`StorefrontThemeSettings` (`storefront_theme_settings_v1`) has a tenant primary key, version, draft/published JSONB, publication revision/time and last editor. `StorefrontThemeCommand` (`storefront_theme_commands_v1`) has `(business_id,idempotency_key)` primary key, operation, canonical request hash, immutable result, actor and creation time. No receipts are evicted. A different actor/body/operation reusing a key returns 409. The original actor with current write access can replay the exact command after newer changes and receive the original receipt; the editor subsequently fetches current state so it never hydrates that old result as the current version.

Writes lock the existing Business row to serialize first insert as well as later writes, then recheck access. Version mismatch returns 409 and performs no state change. Both settings and receipt commit in the caller's transaction; no service commits independently. Versions monotonically increase for save and publish, with a bounded upper limit. Receipt records provide actor/operation attribution without inventing a shared audit schema.

The browser persists only an outstanding command in sessionStorage under `munimjee.v1.theme-command:<user>:<business>`. It stores a hash of the session CSRF value, not the token itself, and a payload digest. Startup validates identity, tenant, schema, digest and a seven-day recovery window before enabling retry. It never replays automatically. Storage failure sends no new command. A terminal identity fence clears every owned theme prefix, the form, preview and displayed private state; generation checks and post-response session checks prevent delayed responses from restoring private data. Preparation/retry locks prevent rapid actions from issuing competing keys. A stale-write response requires explicit reload. This page offers saved-draft preview, with unsaved changes clearly labelled until saved.

## Integrator hooks (not edited by this lane)

1. Reserve an Alembic revision and predecessor in `docs/v1-wave3-contracts.md`. No migration number or predecessor is invented here. Create both tables exactly from the owned model, with PostgreSQL JSONB and check/FK/primary-key constraints, through actual Alembic DDL. Add `app.models.storefront_theme_v1` to the shared model registration import set. Do not use `create_all` as migration evidence.
2. Mount `app.api.v1.theme_settings.router` in the canonical app. Include the three owned static files in runtime packaging. The existing shared private-route no-store error middleware must cover these private APIs/pages, including authentication failures.
3. Add a native workspace link to `/v1/businesses/{id}/themes` from the shared seller shell and catalogue. The page already links back to Catalogue.
4. Extend shared `v1_client.js` private draft cleanup to include `munimjee.v1.theme-command:` alongside the existing catalogue prefix (and separately agreed import prefix), including login/logout and invitation identity switches. The owned page separately clears all theme commands on identity loss.
5. In `PublishedStorefrontProvider.public_store`, **after existing store/tenant publication authorization**, call `config = await published_theme(db, store.seller_id)` from the owned service. Set `PublicStorefront.theme=config['theme']`; use a new explicitly allowlisted design/config field on that internal dataclass/public-page contract for the remaining keys. Never call `read_settings` or expose `draft`, tenant IDs, editor, command receipts or version history publicly. Keep payment-method composition with the catalogue/payment owner.
6. In shared SSR/live rendering, consume the validated published design allowlist only. Map the three palettes to predefined CSS classes/tokens; never interpolate raw CSS. Set configured brand/story/hero/collection text with escaped SSR and DOM textContent. Blank values use each existing theme default. `show_story` and `show_categories` only affect presentation; neither may remove product URLs or alter publication/checkout capability. Keep all existing COD checkout/status/uncertain replay semantics. Query parameters and private preview flags must not enable public checkout.

Until steps 1–6 are integrated and actual DB/native/public checks pass, the editor/module evidence is not a claim that public seller-selected themes work in the mounted application. Provider-hook integration must additionally prove save-draft/public-unchanged, explicit publish/public-updated, all three themes and preserved actual COD privacy/authority.
